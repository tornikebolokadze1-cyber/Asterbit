# FILES — ყველა ფაილი: რისთვისაა და რას აკეთებს

> **ვისთვის:** მფლობელისა და თანამშრომლებისთვის — ვისაც პროექტის აგებულების გაგება სჭირდება.
> **წესი:** ფაილის დამატების, გადატანის ან სახელის შეცვლისას ეს რუკა იმავე ცვლილებაში ახლდება. ყველა ბმული რეპოს ფაილზე მიუთითებს.

რეპოში ფაილები ოთხ ჯგუფად იყოფა. პირველი ადამიანებისთვისაა: სახელმძღვანელო, შეთანხმება, თანამშრომლის გზამკვლევი და დღიური. მეორე Claude-ისთვისაა: წესები, ეტაპების ბრძანებები და დამხმარე აგენტები. მესამე პროექტის ოფიციალური ჩანაწერებია: სად ვართ, რა გადავწყვიტეთ, რა დარჩა და რა გვახსოვს. მეოთხე ძრავის ბიბლიოთეკაა: ცარიელი ფორმები (თარგები), დიზაინები და კვლევა. თითქმის ყველა ფაილი markdown-ია (ჩვეულებრივი ტექსტი სათაურებით, სიებითა და ცხრილებით), ამიტომ VS Code-შიც, Obsidian-შიც და GitHub-ზეც ერთნაირად იკითხება.

## მთავარი საქაღალდე

- [`PROCESS.md`](../PROCESS.md) — სამუშაო შეთანხმება: ხუთი ძირითადი წესი, თითოეული ეტაპი (რას აკეთებს Claude, რას — მფლობელი, რა რჩება შედეგად, როდის მთავრდება), სესიის რიტმი, ხარისხის კონტროლი, როლები და ის, რას სჭირდება მფლობელის თანხმობა. მფლობელის დამტკიცების შემდეგ მისი შეცვლა მხოლოდ ADR-ით შეიძლება. CLAUDE.md იმავე წესებს ინგლისურად ამბობს; თუ ორი ფაილი ერთმანეთს არ ემთხვევა, ეს ხარვეზია.
- [`PROGRESS.md`](../PROGRESS.md) — პროექტის დღიური ოთხი ნაწილით: სად ვართ, რა გაკეთდა (თარიღებითა და commit-ებით), რა მიმდინარეობს და რა არის შემდეგი. ჩანაწერები მხოლოდ ემატება. Claude მას სესიის დასაწყისში კითხულობს და ყოველი ეტაპის ბოლოს ავსებს.
- [`CONTRIBUTING.md`](../CONTRIBUTING.md) — თანამშრომლის გზამკვლევი: გუნდი, რა უნდა დააყენო, როგორ ჩამოტვირთო, როგორ შეიტანო ცვლილება PR-ით და რა უსაფრთხოების წესები მოქმედებს.
- [`CLAUDE.md`](../CLAUDE.md) — Claude-ის სამუშაო წესები ინგლისურად. ეს ერთადერთი ინსტრუქციების ფაილია, რომელსაც Claude Code **სრულად და ავტომატურად** კითხულობს ყოველი სესიის დასაწყისში და ყოველი შეკუმშვის შემდეგ (skill-ებიდან და აგენტებიდან ავტომატურად მხოლოდ მოკლე აღწერები იტვირთება), ამიტომ განზრახ მოკლეა. შიგნით წერია: ვინ არის მფლობელი და ვინ თანამშრომელი; კარიბჭის წესები; ADR-ების წესები; მოდელების როლები; „მზადაა" მხოლოდ ნაჩვენები შედეგით; მეხსიერების წესები; შეკუმშვის ინსტრუქცია (Compact instructions); უსაფრთხოების წესები, რომლებიც ყველა კომპიუტერზე მოქმედებს.
- [`.gitignore`](../.gitignore) — ფაილები, რომლებიც git-ში არასდროს უნდა მოხვდეს: საიდუმლოებები (`.env`, გასაღებები), კომპიუტერისა და რედაქტორის ნაგავი, Claude-ის პირადი ფაილები, შეკუმშვის ნედლი handoff-ები, plugin-ების დროებითი ფაილები (`.omc/`), Obsidian-ის ფანჯრების მდგომარეობა და მომავალი build-ის ნაგავი.

## `.claude/skills/` — 11 ბრძანება

Skill (უნარი) არის საქაღალდე, რომელშიც `SKILL.md` დევს. ფაილის თავში ორ `---` ხაზს შორის სახელი და აღწერაა (front matter). აღწერის მიხედვით Claude თვითონ წყვეტს, როდის ჩატვირთოს skill; ადამიანსაც შეუძლია მისი გამოძახება `/სახელი`-თ. გამოძახებამდე კონტექსტში მხოლოდ მოკლე აღწერა დევს, ამიტომ skill-ები იაფია.

- [`sdlc-status`](../.claude/skills/sdlc-status/SKILL.md) — „სად ვართ?": კითხულობს ფაზების ტაბლოს, `memory/now.md`-ს და ბოლო სესიის შეჯამებას, ამოწმებს git-ს და 12 ხაზში ამბობს მიმდინარე ეტაპს, ბოლო დამტკიცებას, რა აბრკოლებს შემდეგ კარიბჭეს და **ერთ** შემდეგ ნაბიჯს.
- [`sdlc-intent`](../.claude/skills/sdlc-intent/SKILL.md) — Phase 1: იდეა `docs/intent.md`-ად იქცევა. ინტერვიუ რაუნდებად მიდის (მაქსიმუმ 4 კითხვა) შვიდ თემაზე; ბოლოს Claude 3–5 საკუთარ იდეას სთავაზობს, auditor ამოწმებს და მფლობელი ამტკიცებს.
- [`sdlc-architecture`](../.claude/skills/sdlc-architecture/SKILL.md) — Phase 2: გადაწყვეტილებების სია (პლატფორმა, ენა, მონაცემები, hosting, AI მოდელი…). თითოეულზე `architect` 2–3 შემოწმებულ ვარიანტს ამზადებს, მფლობელი ირჩევს, Claude ADR-ს წერს.
- [`sdlc-harness`](../.claude/skills/sdlc-harness/SKILL.md) — Phase 3: ავტონომიის დონე, უფლებები (allow / ask / deny), დაცული ფაილები, hook-ები, მეხსიერების პარამეტრები; თუ პროდუქტი აგენტია, იგივე თავად აგენტისთვისაც. ყოველი დამბლოკავი წესი საცდელად მოწმდება. აქ შეიქმნება `.claude/settings.json`.
- [`sdlc-spec`](../.claude/skills/sdlc-spec/SKILL.md) — Phase 4: `docs/spec.md` ერთ ჯერზე; ყოველ მოთხოვნას ID (FR-1, NFR-1…) და შემოწმებადი კრიტერიუმი აქვს, პრობლემური ადგილები წინასწარ მოინიშნება.
- [`sdlc-plan`](../.claude/skills/sdlc-plan/SKILL.md) — Phase 5: `docs/plan.md` და `tasks/todo.md`. გეგმა „დაიკითხება" (რა გაფუჭდება, რომელია ყველაზე სარისკო ნაბიჯი, რას ამოვაგდებთ), დავალებები კი პატარაა და თითოეულს შემოწმების ბრძანება აქვს.
- [`sdlc-build`](../.claude/skills/sdlc-build/SKILL.md) — Phase 6: კოდირების ციკლი — ჯერ ტესტი, რომელიც ვერ გადის, მერე მინიმალური კოდი, მერე შემოწმება (3 ცდის შემდეგ Claude ჩერდება და კითხულობს), გამარტივება, ჩანაწერი და commit. ეტაპის ბოლოს verifier და auditor, ბოლოს — დემო.
- [`sdlc-evaluate`](../.claude/skills/sdlc-evaluate/SKILL.md) — Phase 7, ორი რეჟიმით: „დაგეგმვა" Spec-ის შემდეგ (თითო კრიტერიუმზე ყველაზე იაფი საიმედო შემოწმება) და „გაშვება" კოდირებისას. „ვერ გაეშვა" გავლად არასდროს ითვლება.
- [`sdlc-secure`](../.claude/skills/sdlc-secure/SKILL.md) — Phase 8: საფრთხეების მოდელი, თითო საფრთხეზე კონტროლი, `/security-review`, საიდუმლოებების სკანირება და ყოველი კონტროლის საცდელი შემოწმება.
- [`sdlc-observe`](../.claude/skills/sdlc-observe/SKILL.md) — Phase 9: ლოგები, ხარჯის აღრიცხვა, საკონტროლო ზოლები და განგაში — რომ ნებისმიერ დროს გავიგოთ, რა გააკეთა აგენტმა და რა დაჯდა.
- [`sdlc-wrap`](../.claude/skills/sdlc-wrap/SKILL.md) — სესიის დასასრული: handoff-ებიდან ერთი შეჯამება, „შეცვლილი აზრის" შედარება მოქმედ ADR-ებთან, გაკვეთილები, `now.md`-ისა და `PROGRESS.md`-ის განახლება, ძველი handoff-ების არქივი და checkpoint.

## `.claude/agents/` — სამი დამხმარე აგენტი

Subagent (დამხმარე აგენტი) ცალკე Claude-ია საკუთარი კონტექსტით: მთავარი საუბრის მსჯელობას ვერ ხედავს, საკუთარი მოდელი და შეზღუდული ხელსაწყოები აქვს და მთავარ სესიას მხოლოდ შედეგს უბრუნებს. ასე შემმოწმებელი ავტორისგან დამოუკიდებელია, მთავარი კონტექსტი კი სუფთა რჩება.

- [`architect.md`](../.claude/agents/architect.md) — Opus 5.5, მაღალი effort; მხოლოდ კითხვა და ვებში ძიება. ერთ გადაწყვეტილებაზე 2–3 ნამდვილ ვარიანტს იძლევა წყაროებით, პლუსებით, მინუსებით, ფასით, რისკით და შექცევადობით, ბოლოს — რეკომენდაციას. გადაუმოწმებელს „UNVERIFIED"-ით ნიშნავს.
- [`auditor.md`](../.claude/agents/auditor.md) — Opus 5.5, მაღალი effort. ყოველ კარიბჭეზე და ყოველი ეტაპის კოდზე ამოწმებს სისრულეს, ზედა დოკუმენტებთან თანხვედრას და მტკიცებულებებს. პირველი ხაზი: `VERDICT: PASS / PASS-WITH-FINDINGS / FAIL / INCONCLUSIVE`. არასდროს ასწორებს და არასდროს ამტკიცებს.
- [`verifier.md`](../.claude/agents/verifier.md) — Sonnet 5.5, საშუალო effort. სუფთა კონტექსტში უშვებს გეგმის შემოწმების ბრძანებებს და თითოეულზე წერს MATCH / MISMATCH / COULD-NOT-RUN; „VERIFIED" მხოლოდ მაშინ, როცა ყველაფერი დაემთხვა.
