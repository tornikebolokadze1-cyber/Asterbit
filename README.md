# Asterbit — ჩვენი AI-native SDLC ძრავა

> **სტატუსი:** ძრავა v0. ჩონჩხი `main`-შია საერთო საფუძვლად; ADR-0001…0003 და PROCESS.md მფლობელის დამტკიცებას ელოდება. პროდუქტი ჯერ არ არჩეულა — მას Phase 1 (Intent) გადაწყვეტს.
> **თანამშრომლებისთვის:** დაიწყე [CONTRIBUTING.md](CONTRIBUTING.md)-ით — იქ წერია, რა დააყენო, როგორ ჩამოტვირთო და როგორ შეიტანო ცვლილება.

## რა არის ეს

წარმოიდგინე სამშენებლო კომპანია, რომელიც სახლს „თვალზე" არასდროს იწყებს. ჯერ შენთან ერთად აყალიბებს, როგორი სახლი გინდა. მერე ირჩევს მასალასა და კონსტრუქციას, აწესებს სამშენებლო მოედნის წესებს (ვინ სად შედის, რა არის აკრძალული), ხაზავს ნახაზს და ადგენს სამუშაო გრაფიკს. მშენებლობისას ოსტატი ყოველ სართულს ამოწმებს, ბოლოს კი ინსპექცია მთელ შენობას ამოწმებს და სიგნალიზაციასა და კამერებს დგამს.

ეს რეპოზიტორია (repository — პროექტის საქაღალდე, რომლის ისტორიასაც git ინახავს) ზუსტად ასეთ პროცესს აწყობს Claude Code-თან მუშაობისთვის. ამას SDLC ჰქვია (Software Development Life Cycle — პროგრამის სასიცოცხლო ციკლი, იდეიდან გაშვებამდე და შემდეგ მოვლამდე). ყოველი ეტაპი ერთი ჩაწერილი დოკუმენტით მთავრდება — ამას artifact ჰქვია (ეტაპის „ხელმოწერილი" შედეგი) — და შემდეგი ეტაპი სწორედ მისი წაკითხვით იწყება.

იდეა Anthropic-ის 2026 წლის აგვისტოს „AI-native SDLC playbook"-ს ეფუძნება: კოდის წერა აღარ არის ყველაზე ნელი ნაწილი, ამიტომ ხარისხი იქ წყდება, სადაც ადამიანი გადაწყვეტილებას იღებს — კარიბჭეებზე (gate — წერტილი, სადაც შენ ამტკიცებ ან აბრუნებ). Claude წერს, ამოწმებს და გთავაზობს; შენ წყვეტ.

სრული სამუშაო შეთანხმება — ვინ რას წყვეტს, როგორ მიდის სესია და რას სჭირდება შენი თანხმობა — [PROCESS.md](PROCESS.md)-შია. რა გაკეთდა და რა დარჩა, ამას [PROGRESS.md](PROGRESS.md) აჩვენებს.

ყველა კარიბჭეს შენ ამტკიცებ. დამტკიცებამდე Claude დამოუკიდებელ აუდიტორს (Opus 5.5) აჩვენებს ნამუშევარს და მის დასკვნას შენც გაჩვენებს. ციკლი გაშვებით არ მთავრდება: ყოველი ახალი იდეა, შეცდომა ან განგაში ახალ intent-ად იქცევა (`docs/changes/NNNN-სახელი/intent.md`) და წრე თავიდან იწყება.

**ერთი ცვლილება შენს თანმიმდევრობაში — რეკომენდაცია:** შეფასების (Phase 7) *დაგეგმვა* ჯობს Spec-ის შემდეგ მოხდეს, როცა უკვე ვიცით, რას ვაშენებთ, რათა კარიბჭეები გეგმაში მოხვდეს და კოდირებისას უკვე მუშაობდეს. *გაშვება* კი კოდირების დროს და გამოშვებამდე ხდება. ასე შენი პირობაც სრულდება — ვარიანტებს მაშინ შემოგთავაზებ, როცა იდეა და სხვა ეტაპები უკვე გავლილია — და შეცდომაც დროულად დაიჭირება. თუ გინდა, რომ ზუსტად შენი თავდაპირველი თანმიმდევრობით წავიდეთ, ერთი სიტყვით შევცვლი.

## ვინ რას აკეთებს — ორკესტრაციის პირველი ეტაპი

მთავარი კოდერია Sonnet 5.5 მაღალ effort-ზე (effort — რამდენ „ფიქრს" ხარჯავს მოდელი თითო ნაბიჯზე). Opus 5.5 ორ როლს ასრულებს. პირველი როლია მრჩეველი: Claude Code-ის advisor tool-ის საშუალებით (ჩაშენებული ხელსაწყო, რომლითაც მთავარი მოდელი უფრო ძლიერ მოდელს ეკითხება) Sonnet მას გადამწყვეტ მომენტებში თავად ეკითხება — მიდგომის არჩევამდე, შეცდომის განმეორებისას და სანამ იტყვის „მორჩა". მეორე როლია აუდიტორი: ცალკე, სუფთა კონტექსტში ამოწმებს ყოველ კარიბჭესა და ყოველ ეტაპს, რათა ავტორმა საკუთარ ნამუშევარს ნიშანი თვითონ არ დაუწეროს.

მომავალში (ახლა არა) კოდს Opus 5.5 და Sonnet 5.5 დაწერენ, არქიტექტურასა და review-ს კი Fable 5.1 და ChatGPT 6.1 Astra შეამოწმებენ. დეტალები: [ADR-0003](docs/decisions/0003-model-orchestration-phase-1.md) და [ორკესტრაციის დიზაინი](sdlc/design/orchestration-and-loop.md).

## მეხსიერება ერთი აბზაცით

ყველა მეხსიერება ჩვეულებრივი markdown ფაილებია git-ში: მათი წაკითხვა შენც შეგიძლია და ისტორია არასდროს იკარგება. ნებისმიერი დამატებითი ინსტრუმენტი (ძიება, გრაფი) მხოლოდ ინდექსია ამ ფაილებზე, რომლის წაშლა და თავიდან აგება ნებისმიერ დროს შეიძლება. ყოველ შეკუმშვამდე (compaction — როცა საუბარი ძალიან დიდდება და Claude მას მოკლე შეჯამებით ცვლის) handoff (გადაცემის ჩანაწერი) იწერება, სესიის ბოლოს — შეჯამება, დროდადრო კი ყველაფერი ერთ მოკლე „ახლანდელ მდგომარეობად" (`memory/now.md`) იკუმშება. ინტერვიუთი შევთანხმდით: შეკუმშვა 65%-ზე, Obsidian-ის ვაულტი, ჯერ ჩვეულებრივი ძიება (QMD — მოგვიანებით, საჭიროებისას) და შეცვლილი აზრის კონტროლი ADR-ებით, git-ითა და სესიის ბოლოს შემოწმებით. დეტალები: [მეხსიერების დიზაინი](sdlc/design/memory-and-context.md), [ADR-0004](docs/decisions/0004-context-and-memory.md).

## რით დავიწყოთ

პირველ რიგში წაიკითხე ეს README, [PROCESS.md](PROCESS.md) (ჩვენი სამუშაო შეთანხმება), [docs/FILES.md](docs/FILES.md) (ყველა ფაილის ახსნა), [ძრავის შერჩევა](sdlc/research/engine-selection.md) და [მეხსიერების დიზაინი](sdlc/design/memory-and-context.md). მეხსიერების ინტერვიუ ჩატარდა, პრინციპები ჩაწერილია, harness აწყობილია: პარამეტრები და ავტომატური hook-ები (hook — ავტომატური ჩამრთველი, რომელიც განსაზღვრულ მომენტში თავისით ეშვება). შემდეგია ძრავის გამოცდა სატესტო, „სათამაშო" იდეაზე; მხოლოდ ამის მერე გადავალთ ნამდვილ პროდუქტზე.

ნებისმიერ დროს თქვი `/sdlc-status` ან უბრალოდ „სად ვართ?" — Claude გეტყვის მიმდინარე ეტაპს და ერთ შემდეგ ნაბიჯს.
